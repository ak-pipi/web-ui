# 玩家代理权限与房费返佣设计文档

> 适用范围：`web_ui/web-ui` 管理后台功能设计，并同步给 `web_server`、`client_cocos`、`server` 做接口和数据支撑。  
> 当前版本：v0.3  
> 目标：在现有 RuoYi-Vue 管理后台中实现玩家代理体系、邀请码绑定、房费积分返佣、积分调整、解绑闭环和分层统计。

---

## 1. 背景与现有基础

### 1.1 现有工程能力

当前工作区包含：

| 项目 | 现状 |
|---|---|
| `web_ui/web-ui` | Vue 2 + Element UI + RuoYi-Vue，已有动态路由、菜单权限、玩家列表、游戏房间列表。 |
| `web_server/web-server` | Spring Boot + MyBatis-Plus，已有管理员 JWT、玩家 JWT 双认证；已有 `agency`、`player.agency_id`、`agency_reward`、`agency_collect`、`capital`、`wallet_ledger`、`room_fee_ledger` 等基础表和部分服务。 |
| `client_cocos/client-cocos` | 玩家端已有登录/注册、个人中心展示 `agencyId`/`agencyName`，但注册和绑定入口没有邀请码。 |
| `server/` | C++ 游戏服负责游戏逻辑；已有 `WalletEventTask` 能发布 `GAME_WIN`、`GAME_LOSE`、`ROOM_FEE` 类钱包事件。 |

### 1.2 现有代理能力

`web_server` 目前已有玩家端接口 `/player/agency/*`：

| 能力 | 现状 |
|---|---|
| 绑定上级代理 | 通过上级玩家 ID 绑定，不是邀请码。 |
| 查看代理信息 | 返回代理等级、下级人数、奖励信息。 |
| 查看直接下级 | 只能看直接下级玩家。 |
| 设置下级代理 | 当前代理可以把直属玩家升为下级代理，旧逻辑限制到 3 级。 |
| 代理奖励领取 | 使用 `agency_reward` 和 `agency_collect`，最终加到 `capital.deposit`。 |

现有实现不足以支撑本次需求：

- 缺少管理后台侧代理树、层级分组、比例配置、解绑闭环。
- 缺少唯一邀请码和通过邀请码绑定。
- 缺少按房费流水逐层拆分的返佣计算和明细。
- 缺少代理管理后台账号与玩家代理身份的关联。
- 缺少代理可见数据范围控制、积分调整额度控制和审计。

## 2. 业务角色与权限模型

### 2.1 角色定义

| 角色 | 身份来源 | 权限范围 |
|---|---|---|
| 超级管理员 | 现有 `sys_user` 超级管理员角色，默认 `admin` | 查看和操作全平台代理、玩家、返佣、积分和解绑。 |
| 一级游戏代理 | 玩家账号 + 绑定一个后台 `sys_user` 账号 + `AGENT_L1` 角色 | 管理自己线路内的二级代理、玩家、返佣比例、玩家积分调整、解绑。 |
| 二级游戏代理 | 玩家账号 + 绑定一个后台 `sys_user` 账号 + `AGENT_L2` 角色 | 管理自己线路内的下级二级代理、玩家、邀请码、返佣明细、玩家积分调整。 |
| 普通玩家 | `player` 表玩家 | 可通过邀请码绑定代理；不登录管理后台。 |

说明：

- 业务只暴露“一级代理”和“二级代理”两种代理身份。
- 二级代理可以继续发展下级二级代理。也就是说代理树深度可以超过 2，但从第 2 层开始业务身份都显示为“二级代理”。
- 超级管理员是平台根节点，默认持有 100% 房费分配权。可使用虚拟根代理 `0000000000` 代表平台收入。

### 2.2 后台账号与玩家代理的映射

管理后台仍沿用 RuoYi 的 `sys_user` 登录和动态菜单权限。代理人员如果需要登录 `web_ui`，需要创建或绑定一个后台账号。

新增映射表建议：

| 表 | 说明 |
|---|---|
| `sys_user_agent` | 关联 `sys_user.user_id` 与 `player.id`，用于把后台登录用户映射到代理玩家身份。 |

核心字段：

| 字段 | 说明 |
|---|---|
| `user_id` | 后台用户 ID。 |
| `player_id` | 代理玩家 ID。 |
| `agent_role` | `SUPER` / `L1` / `L2`。 |
| `status` | `0` 正常，`1` 停用。 |
| `create_by` / `create_time` | 审计字段。 |

### 2.3 菜单与按钮权限

新增一级菜单：`代理管理`，建议挂在现有 `游戏管理` 下或独立一级目录。

| 页面 | 路由 | 权限标识 |
|---|---|---|
| 代理线路 | `/niuma/agency/tree` | `niuma:agency:tree` |
| 代理列表 | `/niuma/agency/list` | `niuma:agency:list` |
| 邀请码管理 | `/niuma/agency/invite` | `niuma:agency:invite` |
| 玩家绑定 | `/niuma/agency/bindings` | `niuma:agency:binding:list` |
| 返佣明细 | `/niuma/agency/commission` | `niuma:agency:commission:list` |
| 积分明细 | `/niuma/agency/wallet-ledger` | `niuma:agency:wallet:list` |
| 积分调整 | 按钮权限 | `niuma:agency:wallet:adjust` |

| 统计报表 | `/niuma/agency/stats` | `niuma:agency:stats` |

按钮权限：

| 操作 | 权限标识 | 角色 |
|---|---|---|
| 设置一级代理 | `niuma:agency:create:l1` | 超级管理员 |
| 设置二级代理 | `niuma:agency:create:l2` | 超级管理员、一级代理、二级代理 |
| 修改返佣比例 | `niuma:agency:rate:update` | 超级管理员、一级代理、二级代理 |
| 生成/重置邀请码 | `niuma:agency:invite:update` | 超级管理员、代理本人、其直属上级 |
| 玩家积分加减 | `niuma:agency:wallet:adjust` | 超级管理员、代理 |
| 解除绑定 | `niuma:agency:unbind:execute` | 超级管理员、一级代理 |
| 导出 | `niuma:agency:export` | 超级管理员、一级代理 |

## 3. 代理树与绑定规则

### 3.1 层级规则

代理树根为平台：

```text
平台/超级管理员(100%)
  一级代理A(90%)
    二级代理B(80%)
      二级代理C(70%)
        普通玩家P
```

字段含义：

- 每个代理有一个“自身返佣比例” `commission_rate_bp`，单位为 bp，10000 表示 100%。
- 比例由上级设置，且必须小于等于上级自己的比例。
- 平台根节点固定 10000 bp。
- 一级代理的上级是平台根节点。
- 二级代理的上级可以是一级代理，也可以是另一个二级代理。

### 3.2 创建代理规则

| 操作人 | 可设置对象 | 限制 |
|---|---|---|
| 超级管理员 | 普通玩家 -> 一级代理 / 二级代理 | 设置一级代理时上级为平台；设置二级代理时必须指定上级代理。 |
| 一级代理 | 自己线路内普通玩家 -> 二级代理 | 目标玩家必须已绑定在该一级代理线路内。 |
| 二级代理 | 自己线路内普通玩家 -> 二级代理 | 目标玩家必须已绑定在该二级代理线路内。 |

校验：

- 目标玩家必须存在、未封禁、未删除、不是机器人。
- 目标玩家不能已经是代理。
- 不能形成循环线路。
- 不能跨线路提拔玩家。
- 创建代理时必须设置 `commission_rate_bp`，且 `0 <= 子代理比例 <= 当前代理比例`。

### 3.3 邀请码规则

| 规则 | 说明 |
|---|---|
| 唯一性 | 全平台唯一，建议 6-10 位大写字母和数字。 |
| 归属 | 邀请码归属于代理玩家。 |
| 状态 | `active` / `disabled` / `expired`。 |
| 使用方式 | 玩家注册时填写，或登录后在个人中心绑定。 |
| 绑定限制 | 每个玩家同一时间只能绑定一个上级代理。 |
| 解绑后重绑 | 默认需要超级管理员或原线路一级代理审批后才能重绑。 |

邀请码生成建议：

- 默认每个代理保留一个 active 邀请码。
- 支持管理员重置邀请码，旧码置为 `disabled`。
- 为推广统计可支持多邀请码，同一代理可创建不同渠道码。

### 3.4 玩家绑定关系

当前 `player.agency_id` 可继续作为“当前直接上级代理”兼容字段，但必须新增绑定历史表，避免解绑/重绑后历史收益丢失。

绑定状态：

| 状态 | 说明 |
|---|---|
| `active` | 当前有效绑定。 |
| `unbound` | 已解除。 |
| `pending_unbind` | 解绑待处理。 |
| `rejected` | 解绑申请被拒。 |

绑定校验：

- 玩家不能绑定自己。
- 玩家不能绑定非代理。
- 玩家不能绑定封禁或停用代理。
- 玩家已是代理时，可以绑定上级代理；但需要按代理树校验，不能跨线形成循环。
- 玩家参与中的房间不影响绑定，但房费返佣以房费流水产生时的绑定快照为准。

## 4. 房费积分返佣规则

### 4.1 名词统一

| 名词 | 本设计含义 | 当前系统落点 |
|---|---|---|
| 游戏积分 | 玩家参与游戏输赢的积分 | 当前可对应 `capital.gold`。 |
| 房费积分 | 房间产生的房费抽取金额 | 当前进入 `room_fee_ledger.fee_amount`，或由 `WalletChangeEvent` 的 `ROOM_FEE` 表示。 |
| 代理返佣 | 房费积分按代理线路比例拆分后的收益 | 新增 `agency_commission_ledger`；当前实现入账到收益方 `capital.deposit`。 |
| 平台积分池 | 平台/超级管理员持有的系统根积分 | 使用虚拟根玩家 `0000000000` 的 `capital` 记录。新库初始 500000000 积分全部在该账户。 |

MVP 建议：

- 玩家游戏输赢继续走 `WalletChangeEvent` 和 `walletService`，钱包类型用 `gold`。
- 人工积分分配不允许增发或销毁：加分时从操作人的资金账户扣，减分时返还给操作人的资金账户。
- 超级管理员的资金账户是平台根玩家 `0000000000`；代理后台账号的资金账户是其绑定的代理玩家。
- 房费返佣先写 `agency_commission_ledger`，并同步写 `wallet_ledger`，业务类型为 `agency_commission`；平台分成也写入 `0000000000` 的钱包流水。

### 4.2 分账公式

对一笔房费 `feeAmount`，找到付费玩家当前有效绑定线路：

```text
平台(rootRate=100%)
  -> 一级代理A(rate=90%)
  -> 二级代理B(rate=80%)
  -> 二级代理C(rate=70%)
  -> 付费玩家P
```

各层收益：

| 收益方 | 公式 | feeAmount=10 示例 |
|---|---|---|
| 平台/超级管理员 | `(100% - A.rate) * feeAmount` | 1 |
| A | `(A.rate - B.rate) * feeAmount` | 1 |
| B | `(B.rate - C.rate) * feeAmount` | 1 |
| C | `C.rate * feeAmount` | 7 |

如果玩家直接绑定到一级代理 A，且 A.rate=90%：

| 收益方 | 收益 |
|---|---|
| 平台 | `10 * (100% - 90%) = 1` |
| A | `10 * 90% = 9` |

如果玩家没有绑定代理：

| 收益方 | 收益 |
|---|---|
| 平台 | 100% |

### 4.3 比例约束

新增或修改下级比例时：

```text
0 <= childRate <= parentRate <= 10000
```

若某代理已有下级，则调低该代理比例时必须满足：

```text
newRate >= max(activeChildRate)
```

否则会导致旧下级比例超过上级，必须先调整下级比例。

### 4.4 整数积分取整

为了保证一笔房费 100% 分完：

1. 比例用 bp 存储，避免浮点误差。
2. 按线路从上到下计算差额比例。
3. 非最后一层使用向下取整。
4. 最后一层代理获得剩余金额。
5. 没有代理时平台获得全部。

每条返佣明细必须保存：

- 当前层代理 ID。
- 当前层比例。
- 下级比例。
- 实际分得比例。
- 房费原始金额。
- 实际返佣金额。
- 线路快照。

### 4.5 幂等与冲正

返佣计算以 `room_fee_ledger.id` 为幂等源。

建议唯一键：

```text
uk_fee_agent(room_fee_ledger_id, agent_player_id)
```

异常场景：

| 场景 | 处理 |
|---|---|
| 结算消息重复 | 命中唯一键后跳过返佣生成。 |
| 房费流水冲正 | 新增负向 `agency_commission_ledger`，不要物理删除原记录。 |
| 代理解绑后历史房费补单 | 使用房费产生时间点的绑定快照，不能按当前绑定关系重算。 |
| 比例修改后历史补单 | 使用房费产生时间点的比例快照；如果没有快照，按当前比例并标记 `snapshot_missing`。 |

## 5. 数据模型设计

### 5.1 复用现有表

| 表 | 使用方式 |
|---|---|
| `player` | `agency_id` 保留为当前直接上级代理，供现有玩家端兼容。 |
| `agency` | 继续作为代理主表，扩展比例、状态、邀请码等字段。 |
| `capital` | 当前玩家资产表，平台根账户 `0000000000` 持有初始积分池；代理返佣入 `deposit`，人工调整在 `gold`/`deposit` 中做守恒转账。 |
| `wallet_ledger` | 记录代理返佣入账、玩家积分调整、房费扣减等资产流水。 |
| `room_fee_ledger` | 作为返佣计算的房费来源。 |
| `game_scoreboard` | 用于玩家胜率统计。 |
| `admin_audit_log` | 记录后台操作审计。 |

### 5.2 `agency` 表扩展

建议新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `agent_type` | tinyint | `0` 平台根，`1` 一级代理，`2` 二级代理。 |
| `depth` | int | 树深度，平台 0，一级 1，二级及以下递增。 |
| `path` | varchar(1024) | 物化路径，如 `/0000000000/A/B/`，用于快速查子树。 |
| `commission_rate_bp` | int | 自身返佣比例，0-10000。 |
| `invite_code` | varchar(16) | 当前默认邀请码，可选；多邀请码时放到独立表。 |
| `status` | tinyint | `0` 正常，`1` 停用。 |
| `created_by_user_id` | bigint | 创建该代理的后台用户。 |
| `created_by_player_id` | varchar(32) | 创建该代理的代理玩家。 |
| `create_time` / `update_time` | datetime | 时间字段。 |

兼容说明：

- 旧字段 `superior_id` 保留，表示直接上级代理玩家 ID。
- 旧字段 `level` 可保留，但建议含义调整为树深度；前端显示使用 `agent_type`。
- 旧字段 `junior_count` 可作为缓存字段，最终以绑定表/子树查询为准。

记录玩家与代理的绑定历史。

| 字段 | 说明 |
|---|---|
| `id` | 主键。 |
| `player_id` | 被邀请/绑定玩家。 |
| `agent_player_id` | 直接上级代理玩家 ID。 |

### 5.5 新增 `agency_commission_ledger`

## 9. server 与 MQ 对接边界

需要确认的现有断点：

- `WalletEventTask` 发送 `WalletChangeEvent` 到 `game.direct/web_server_001`。

本功能建议以 `room_fee_ledger` 为唯一返佣源。如果后续启用 `WalletChangeEvent.ROOM_FEE`，必须通过 `biz_id + event_type + player_id` 或单独 `ref_no` 做幂等，避免双算。

## 10. 核心流程

### 10.1 设置一级代理

```text
超级管理员
  -> 选择普通玩家
  -> 设置代理类型=一级代理、比例=90%
  -> 创建/绑定后台账号和角色 AGENT_L1
  -> 写 agency
  -> 生成邀请码
  -> 写审计日志
```

### 10.2 设置二级代理

```text
上级代理/超级管理员
  -> 选择自己 scope 内普通玩家
  -> 设置代理类型=二级代理、比例 <= 上级比例
  -> 写 agency.superior_id、path、depth
  -> 创建/绑定后台账号和角色 AGENT_L2
  -> 生成邀请码
  -> 写审计日志
```

### 10.3 玩家通过邀请码绑定

```text
玩家提交 inviteCode
  -> 查询 active 邀请码
  -> 校验代理有效
  -> 校验玩家未绑定或允许重绑
  -> 写 player_agent_bind active
  -> 更新 player.agency_id
  -> 更新邀请码 bind_count
  -> 更新代理 junior_count 缓存
```

### 10.4 房费返佣

```text
房费流水 room_fee_ledger
  -> 查询 fee_player_id 的 active 绑定
  -> 没绑定：平台收益 100%
  -> 有绑定：获取代理线路和比例
  -> 校验比例单调递减
  -> 生成每层 agency_commission_ledger
  -> 写代理钱包入账流水
  -> 更新统计缓存
```

### 10.5 解绑

```text
一级代理/超级管理员发起
  -> 校验 scope
  -> 校验目标没有未处理解绑单
  -> 校验目标代理是否有活跃下级
  -> 写 agency_unbind_request
  -> 执行解绑
  -> player.agency_id = null
  -> player_agent_bind active -> unbound
  -> 写审计日志
```

## 15. 本次实现补充口径

当前代码实现先按 MVP 闭环落地，规则如下：

1. 房费返佣自动入账到代理玩家 `capital.deposit`，钱包流水业务类型为 `agency_commission`。
2. 平台/超级管理员收益写入 `agency_commission_ledger`，并同步写入虚拟根玩家 `0000000000` 的 `capital.deposit`，保证房费扣除后平台分成不丢失。
3. 历史 `agency` 数据默认 `commission_rate_bp = 0`，必须由超级管理员显式配置后才参与代理分成。
4. 历史 `player.agency_id` 会迁移为 `player_agent_bind` 的 `legacy` 绑定记录，同时保留 `player.agency_id` 作为兼容字段。
5. 每个玩家同一时间只允许一个 `active` 绑定；解除后可保留多条历史记录。
6. 解绑 MVP 采用“申请即审核并执行”的闭环接口，但仍保留申请、审核、执行状态字段，为后续二级审批预留。
